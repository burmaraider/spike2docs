The LCD node board

Batman 66 has a small screen on its playfield that shows clips of the villains ("VILLAIN VISION" in the game's tables). It looks like the small screen of Star Wars, but it is built the other way round. Star Wars' is a second display of the CPU board and the game draws every frame of it. Batman's hangs off a node board, and the game never sends it a picture.

The board, lcdnode, keeps numbered pictures in its own flash memory. The game tells it which one to show, or which run of them to play and how fast, and asks now and then which one is up.

Read this first: nothing here was captured from, or run on, real hardware. On this page everything is read from the software on game cards and from what that software does when it runs against a simulator. Each statement carries one of the tags below.

The board

On the bus
Node address 24 in Batman, board type 17, part 520-6988-XX, firmware name lcdnode, image for an LPC1113. It answers the common commands of every node board (version, status, inputs, reset, boot loader). measured
Screens
Up to four LCDs per board; Batman has one. A string among the game's device names reads "LCD 320X240". game firmware
Timer
Durations are in board ticks, 1280 a second: SysTick with a reload of 0x927b (37500 cycles at 48 MHz), set up at 0x4568. The main loop runs the player and the backlight once each time the tick count changes. The game's eight frame periods come out as 30, 24, 20, 16, 15, 12, 10 and 8 frames a second. firmware game

Commands

All of them are sub-commands of the node service command f2. The game holds one record per LCD (0x38 bytes, table at *0x8716ac); its interface functions only write a request into the record, and one function, 0x498dc0, turns pending requests into messages. A second, 0x498fe8, polls the status. Both are called from 0x292950. game

n is the LCD number 0..3, in the low bits of the sub-command except for the status, where it is a byte of its own. f is a flags byte, always 0 from the requests Batman uses (0x4989f8 would send 0x10): its low three bits are a queue control the board applies before queueing the run, 0x08 puts the run in front of the one playing, and 0x10 plays the inner range back and forth. Numbers are little-endian. The firmware sees the length byte one higher than the game writes it (4, 8, 0xe, 0x18). firmware game

In attract mode Batman runs a slideshow: backlight off, a quarter of a second later a new frame and backlight on, the next change 5.7 seconds after. Frames 2, 54, 720, 591, 601 and 1605 came up in one minute. Starting a game played frames 820 to 830 at 12 a second. measured

Calls with constant arguments, from a scan of the executable: plays of 484 to 496, 1432 to 1434 and 2119 to 2152 (speed 3), 820 to 830, 919 to 928 and 929 to 938 (speed 5), and one-frame plays of 2153 and 2155. One more play takes its first and last frame from a table built at run time (0xb27f0: *(0x8703bc) + 0xa0). Plays usually follow the same pattern: backlight off with ramp 15, a still of the first frame, backlight on, then the play. game

The villain effects are not plays. Frames such as 274/275, 315/317, 334 to 343 and 402/403 are flashed by the game sending stills in a loop with short waits between them (0xa2a84, 0x129404 and others), so on the board they are a series of one-frame runs. game

The board's player

The firmware keeps, for each LCD, a queue of sixteen runs (entries of 0x1c bytes, read and write index wrapping at 15) and steps the one at the head from its timer. firmware

  1. Queueing (0x2eb0). A run is first, last, an inner range, a repeat count, the period and the flags. If last is below first the two are exchanged and the direction becomes -1. The current frame starts at the end the game named first, and the countdown at the period. If the inner range, put in order, is not inside first..last, the repeat is turned off. The low three bits of the flags are then applied as a queue control. A full queue (read index equal to write index while not empty) refuses the run, and the reply carries an error bit. Flag 0x08 puts the run before the head (the read index moves back one); the run it displaces keeps its frame and countdown and continues after it.
  2. Stepping (0x2f8c), once per tick, for the head of every LCD's queue unless it is paused: while the countdown is above zero it is decremented; at zero it is reloaded with the period and the run takes a step. So each frame stays up for period + 1 ticks.
  3. A step forwards. At the end of the inner range with a repeat left, the repeat is counted down. With more passes to go, the frame jumps back to the start of the inner range, or with flag 0x10 the direction turns round. On the last pass it goes on towards last. Otherwise the frame moves up one, and at last the run ends.
  4. A step backwards. The same at the start of the inner range, mirrored: with passes to go the frame jumps to the end of the inner range, or with flag 0x10 the direction turns forwards. On the last pass the direction becomes forwards in either case, so a run played backwards with a repeat finishes going up. Otherwise the frame moves down one, and at first the run ends.
  5. The end (0x2aa8). The read index moves on. If the queue is then empty the LCD is idle and keeps showing the frame it drew last.
  6. Queue control (0x2dc4, jump table at 0x4c50), with runs queued: 0 nothing; 1 the head's repeat becomes 1 (2 when it is going forwards back and forth), so it ends after the current pass; 2 drop the head; 3 empty the queue; 4 pause the head; 5 resume it. With nothing queued only 2 and 3 do anything, and 4 or 5 runs into an undefined instruction.

So a run of N frames takes N periods, and the frame the status reports is the last one of the run from then on. That is what the game's wait relies on: it returns when the reported frame is no longer inside first to last - 1.

Drawing

The firmware writes pixels to the panel as 16 bits (5-6-5) or as 12 bits (4-4-4), depending on a per-LCD setting (0x32d4). Frames come from the flash; nothing is ever drawn from bytes the game sent. A frame is drawn when the head's frame has changed and the previous transfer to the panel has finished (0x3648), so a fast run may skip frames on the board. Frame numbers run through all the picture sets in flash: a number past the end of one set continues in the next. firmware

Backlight

Each LCD's backlight level is kept as level × 0x80 in 16 bits, and the PWM gets the top byte. f2 80 (0x33f8) sets the target. With ramp 0 the level is set at once. Otherwise a step is worked out once: firmware

step = (target - level) × table[ramp] >> 20, at least 1 (or -1 going down)

and every tick (0x3648) the step is added until the level passes the target, which it is then set to. The table at 0x4ca0 holds 51200 / ramp, read as a signed 16-bit number. A full swing between 0 and 0xff therefore takes about ramp × 16 ms: the game's ramp of 15 is about a quarter of a second. Ramp 1 is the exception: 51200 does not fit, reads as -14336, and the level lands on the target on the first tick. firmware

The pictures

The frames live in a flash chip on the board. From the firmware (0x2bf4, 0x2b7c), a picture set begins with a 0x20-byte header: firmware

OffsetSizeField
01Kind. 0xff = no set here. Bit 7 set = frames of different sizes, with a table of offsets; clear = all frames the same size.
22Number of frames

A fixed-size set occupies frames x width x height x ceil(bits / 8) bytes after the header, and the next set starts at the next 0x200-byte boundary.

They are not on the game's card

The one routine in the game that can write the flash is 0x2916b4. It asks the board for the version of its picture set (f2 30), opens a file named after the LCD device with .bin appended, reads a 0x20-byte header from it, and programs the file in 0x200-byte pages (0x5aa7c0), the first page last. game

In Batman 1.14.0 the device's name pointer (0x7c19e4) is null, in the file and at run time, and nothing writes it. The routine returns before it asks the board anything, and no such file exists anywhere on the card. game measured

A dump of 226 Batman frames was supplied separately, as one 320×240 PPM picture per frame number (2, 54, 274 to 3026, with gaps). It covers every frame of the constant plays listed above and of the attract slideshow. It is not part of this project and is not on the card.

The simulator

The recompilation's board model (src/runtime/lcd_node.cpp) is the player above, transcribed: per LCD the queue of sixteen runs with their countdowns, the steps with repeats and both directions, the flags, the queue controls, and the backlight fade. Board time is counted in 1280 Hz ticks from the host clock, and the player and the fade are brought up to date tick by tick whenever the game or the window asks. It answers the status with the frame on the screen, so a run the game waits for takes its real time. model

A window, "SPIKE2 playfield screens", shows each LCD. With --lcd-frames DIR (or a folder lcd_frames beside the executable or in the working directory) holding one <frame>.ppm per frame number, it draws the frame's picture; without one, it draws the frame's number. Either way it is lit as the backlight is lit, and black when the backlight is off. A picture is loaded the first time its frame comes up. The window appears only on a machine whose game addresses such a board. SPIKE2_LCD=0 turns it off.

The log has a line for every play the game asks for (lcd ... play frames A..B), and for the first 40 stills and backlight changes.

Not modelled: the time the board takes to send a picture to the panel (frames are never skipped), the error bit of the reply when the queue is full (the run is dropped and logged), and bytes 4 to 11 of the status reply, which stay zero.
