The LCD node board

Batman 66 has a small screen on its playfield that shows clips of the villains ("VILLAIN VISION" in the game's tables). It looks like the small screen of Star Wars, but it is built the other way round. Star Wars' is a second display of the CPU board and the game draws every frame of it. Batman's hangs off a node board, and the game never sends it a picture.

The board, lcdnode, keeps numbered pictures in its own flash memory. The game tells it which one to show, or which run of them to play and how fast, and asks now and then which one is up.

Read this first: nothing here was captured from, or run on, real hardware. On this page everything is read from the software on game cards and from what that software does when it runs against a simulator. Each statement carries one of the tags below.

The board

On the bus
Node address 24 in Batman, board type 17, part 520-6988-XX, firmware name lcdnode, image for an LPC1113. It answers the common commands of every node board (version, status, inputs, reset, boot loader). measured
Screens
Up to four LCDs per board; Batman has one. A string among the game's device names reads "LCD 320X240". game firmware
Timer
Durations are in board ticks. With 1280 ticks a second, the rate the other boards of this family report, the game's eight frame periods come out as 30, 24, 20, 16, 15, 12, 10 and 8 frames a second. The board's own tick rate was not read. game model

Commands

All of them are sub-commands of the node service command f2. The game holds one record per LCD (0x38 bytes, table at *0x8716ac); its interface functions only write a request into the record, and one function, 0x498dc0, turns pending requests into messages. A second, 0x498fe8, polls the status. Both are called from 0x292950. game

The board's player

The firmware keeps, for each LCD, a queue of sixteen runs (entries of 0x1c bytes, read and write index wrapping at 15) and steps the one at the head from its timer. firmware

  1. Queueing (0x2eb0). A run is first, last, period and a repeat count. If last is below first the two are exchanged and the direction becomes -1. The current frame starts at the end the game named first. A full queue drops the request.
  2. Stepping (0x2f8c), once per tick for every LCD that is not idle: a countdown is decremented; at zero it is reloaded with the period and the current frame moves one step.
  3. The end. When the frame is the last one and the countdown runs out again, the run is over: the read index moves on. If the queue is then empty the LCD is idle and keeps showing that frame.
  4. Queue control (0x2dc4) acts on the run in progress: drop it, empty the queue, stop and resume stepping, or let a repeating run end after its current pass.

So a run of N frames takes N periods, and the frame the status reports is the last one of the run from then on. That is what the game's wait relies on: it returns when the reported frame is no longer inside first to last - 1.

Drawing

The firmware writes pixels to the panel as 16 bits (5-6-5) or as 12 bits (4-4-4), depending on a per-LCD setting (0x32d4). Frames come from the flash; nothing is ever drawn from bytes the game sent. firmware

The pictures

The frames live in a flash chip on the board. From the firmware (0x2bf4, 0x2b7c), a picture set begins with a 0x20-byte header: firmware

01Kind. 0xff = no set here. Bit 7 set = frames of different sizes, with a table of offsets; clear = all frames the same size.

A fixed-size set occupies frames x width x height x ceil(bits / 8) bytes after the header, and the next set starts at the next 0x200-byte boundary.

They are not on the game's card

The one routine in the game that can write the flash is 0x2916b4. It asks the board for the version of its picture set (f2 30), opens a file named after the LCD device with .bin appended, reads a 0x20-byte header from it, and programs the file in 0x200-byte pages (0x5aa7c0), the first page last. game

In Batman 1.14.0 the device's name pointer (0x7c19e4) is null, in the file and at run time, and nothing writes it. The routine returns before it asks the board anything, and no such file exists anywhere on the card. game measured

The simulator

The recompilation's board model (src/runtime/lcd_node.cpp) keeps what the player keeps: per LCD the queue of runs, the frame on the screen worked out from the time since the run began, and the backlight level. It answers the status with the frame, so a run the game waits for takes its real time. model

A window, "SPIKE2 playfield screens", shows each LCD as the number of the frame that is up, lit or dark with the backlight. It appears only on a machine whose game addresses such a board. SPIKE2_LCD=0 turns it off.

Not modelled: the run with an inner range (played once straight through), repeat counts, the backlight ramp, and bytes 4 to 11 of the status reply, which stay zero.
