SPIKE2 Node Boards

How the game talks to its node boards

A SPIKE2 pinball machine has one CPU board running Linux and a chain of small microcontroller boards, the node boards, that read the switches and drive the coils, motors and lamps. The game program never touches a coil itself. It writes bytes to one serial port, and a chip on the CPU board, the net bridge, passes them on to the boards.

This guide is everything this project has recovered about that conversation: the frames, each command and its reply, byte by byte, and the tables inside the game that decide which board is where.

There are two sources, and they are the two ends of the wire. The game side is the game executable of Godzilla LE 1.16.0, read as ARM code, and the same code located in Dungeons & Dragons LE 1.10.0. The board side is the firmware of the boards and of the bridge, taken from the D&D card, decrypted and read handler by handler.

Read this first: nothing here was captured from, or run on, real hardware. A request is what the game's code builds. A reply is what the board's firmware code sends. Both are read from code. The pieces

The drawing shows which boards exist, not how they are cabled. The physical order on the bus was not looked at.

The short version

One master
The game speaks, a board answers. A board never speaks first. A board that has news sets a request flag, the bridge finds it with a poll, and the game then asks it.
Two kinds of frame
A bridge command is for the bridge itself: cmd len data. A node message has bit 7 set in its first byte and is passed to a board: 0x80|addr len cmd args checksum reply_len.
Nine bits on the bus
Between the bridge and the boards an address byte is sent with a ninth bit set. That is how a board tells the start of a message from data.
Checksum
One byte, chosen so that the bytes it covers add up to zero. The same rule guards the reply.
The game says how long the reply is
The last byte of a node message is the number of reply bytes the bridge must collect. There is no length in the reply.
Time is in board ticks
Each board reports a tick rate in its version reply and the game converts every duration with ms * rate / 1000. Driver and stepper boards report 1280 ticks per second, LED boards 60.
Inputs are active low
A bit of 1 is an open input. Every physical switch in Godzilla is active when its bit is 0.
Boards act on their own
A flipper cannot wait for a round trip. The game loads a rule into the board, and the board fires the coil itself when the switch closes.

What happens from power-up?

Each step below is established from the game's code or from recorded traffic. The first and the last two have a known place. The order of the steps between them was only partly written down.

  1. nodebus_open 0x005b5018 exports GPIO 75, opens /dev/ttymxc1 and turns node power on with bridge command 07.
  2. The game reads the bridge version (03). A bridge at 0.3.0 or later has a 4-byte status word.
  3. node_discover 0x002df8dc finds out which listed boards answer. A board that does gets "found" in its record (0x00208f84), and its version is read with fe.
  4. node_grade_firmware 0x002ddf00 compares each version reply with the header of the board's image file on the card. A mismatch, or a board answering from its boot loader, starts a firmware update. See Firmware.
  5. Board set-up 0x002deb78: dimensions (14), fault masks (72, 46), fault time (48), fault detection (44), switch debounce (70).
  6. Self-test: every LED is pulsed once with its mask bit cleared and the board status is read for a fault. Every driver is fired once with a 1-tick pulse.
  7. The last bus action of node_init 0x002dfd40 is bridge command 0b with argument 6, which sets the backbox lamp's PWM period.
  8. From then on the nodebus thread 0x002e0890 polls the bridge (00), reads inputs from boards that ask (11), and the rest of the game sends lamp and driver commands as it pleases.

On the original timing node init takes about 27 s, most of it fixed settle delays.

What is on the wire?

There are two wires. From the game to the bridge: bytes at 460800 baud, 8 data bits, no parity, one stop bit, 21.7 µs per byte. All of it passes through one function, nodebus_exchange_data at 0x005ad984, which calls tcflush(TCIFLUSH), writes the frame, and reads as many reply bytes as the frame asks for. game cross-check

From the bridge to the boards: the same bytes with a ninth bit that marks an address byte. firmware

Multi-byte numbers are little-endian, with one exception: the raw SPI words of commands 20 and 21.

Bridge command

First byte below 0x80. The bridge consumes it; no board sees it.

Command 00, the poll, is the exception: it is that one byte, with no length. A bridge reply is raw data, with no checksum and no status byte. Its length is fixed per command and listed on the Bridge tab.

What the bridge does with it

  1. It sends the address byte to the boards with the ninth bit set, then the length byte and that many bytes as plain data.
  2. It reads the reply length from the game. With 0 the exchange is over.
  3. Otherwise it turns the line round and forwards reply_len − 1 bytes from the board to the game: the data and the board's checksum.
  4. It appends its own status byte.

Each reply byte must arrive within the reply time, 4800 timer counts unless command 06 set another for this one exchange. When a byte does not come, the bridge sends ee in its place, fills the rest of the reply with 55, and sets status bit 2. The game always gets the number of bytes it asked for. firmware

What a board does with a message

Address match
A board takes a message when the address is its own or 0. A broadcast is acted on only for f0 and f1, and never answered.
Checksum
A message whose bytes do not add up to 0 is dropped and fault bit 13 set. The board sends nothing, so the bridge reports a time-out.
Message counter
The board counts messages addressed to itself, not broadcasts. The game keeps the same count at 0x0085545c + 4n. The status reply (ff) returns the board's count and clears it; a count that differs from the game's makes the game treat the node as faulty.
Two buffers
A board holds two messages at a time. A third while both are waiting sets fault bit 20; a message longer than 0x84 bytes sets fault bit 8.
Unknown command
Sets fault bit 17. No reply.
Gate on ordinary commands
On the game's side, commands below 0xf0 are sent only while a per-board word, 0x0071c220[addr] + 0x14, is non-zero. game

Scrambling

With bit 6 of the address byte set, the board descrambles the bytes after the length byte. Byte n of the frame (the address is byte 0) is XORed with two values:

K = (address & 15) << 4 | (len & 15)
plain[n] = wire[n] ^ key[(n - 2) & 15] ^ (n odd ? ~K : K)        ; n >= 2

The key is 16 bytes held by the board and returned by command fc. The game keeps its copy in a table at 0x0085525c, but the per-node enable byte 0x008550e7 + 12n has no writer in this build, so ordinary traffic is never scrambled. The bit does appear on the page data of encrypted firmware images. firmware game

How long does a message take?

Ten bit times per byte on the game's side. The read-inputs exchange above is 5 bytes out and 12 back: 17 bytes, 0.37 ms of wire time, before the bridge's and the board's own turnaround. A write only queues the bytes in the tty; the caller waits when it reads the reply.

The net bridge

The bridge is a small microcontroller on the CPU board at the other end of /dev/ttymxc1. Its firmware, netbridge-0_5_0.hex, sits unencrypted on the root file system under /usr/local/spike. It switches power to the boards, finds the board that wants service, carries every node message, and keeps a status word about all of it. Everything on this tab is read from that firmware. firmware

Poll and service

The nodebus thread sends the single byte 00 again and again. The answer is one byte.

Nothing to report
game →
← bridge
Node 8 has a changed input
game →
← bridge

The game then sends 11 to node 8. Reading the inputs clears the request.

Behind that one byte the bridge runs a binary search. It sends a probe: an address-marked byte with bit 7 clear and a number in it. Every board whose address is not above that number, and which wants service, answers with one byte ff at once. The bridge only listens for whether anything came back, 0x479 counts per probe, and halves the range. Five probes at most find the lowest waiting address among 31.

A board answers a probe only while two of its traffic flags are set: the service request and "may answer polls". See Inputs.

Power and the boot line

Node power and amplifier power are two pins. Turning node power on starts every board.

The boot hold is a break: the bridge holds the bus in the break state for as long as the hold is on. The updater uses it to get one board into its boot loader: it resets the board with f1, turns the hold on, waits 1.25 s and turns it off. That a board's boot loader stays put when it finds the line in break is inferred from this sequence; the boot loader itself is not in any update file. unknown

Every node command

One row per command. The game's node library has one builder function per command; it is not title code and sits at 0x005ad920-0x005b5538 in Godzilla and at 0x005c3c10-0x005cb8e0 in D&D. The board side is a handler in the firmware, found through a table indexed by the command's high nibble.

Layouts show the command byte and its arguments, without the frame around them. "Reply" is the number of data bytes, without checksum and status. "Boards" names the firmware whose handler was read; "all three" means the handler exists in pinnode, ws2812node and tmc5041node and was read in pinnode.

Identity and status replies

fe: version, 11 bytes

  • Version, tick rate and image id are constants in the firmware (0x2ad0). pinnode 1.37.0 sends 01 25 00, 00 05 and 01. firmware
  • The flag is a RAM byte in the application. The game reads bit 7 as "boot loader running" (0x002ddf00).
  • The version and image id must equal the header of the board's image file, or the game re-programs the board. game
  • The MCU part id selects a row of the game's MCU table (0x006adb4c), and with it the firmware family that is part of the image file name.
  • A tick rate of zero disables every timed command on the game's side and makes it ask for the version again before each one.
  • The game also accepts a 10-byte form without the image id, and then asks for it with fa 01.

ff: status, 8 bytes

Switches and other inputs

A node board has up to 64 inputs, sent as 8 bytes. Input n is bit n & 7 of byte n >> 3. A bit of 1 means the input is open. Inside the board the inputs are four 16-bit words, and wherever a command names an input it is as 0x40 | input: bit 6 says "there is an input", bits 4-5 the word, bits 0-3 the bit.

Reading them: command 11

game → node
node → game, 10 data bytes

The first eight bytes are the debounced inputs with the masked ones forced to 0. The last two are a 16-bit word: bits 0-14 count the ticks since the last input change, stopping at 0x7fff, and bit 15 is set when the service request flag is clear. Reading clears the request; an input that changes again sets it again. firmware

From a bit to a switch

Switch number n is the n-th entry of kind 1 in the game's I/O table. The entry names the board and the bit. A second record, 40 bytes at 0x00776b00 + 40n, holds the switch definition.

active = input_bit XOR NOT(definition_flags & 4)        ; 0x00378914

So a switch without flag 4 is active when its bit is 0. In Godzilla that is every physical switch: leaf, micro and opto alike. Only four virtual switches are active-high. game cross-check

Debounce: command 70

70 input on off sets the two debounce times of one input in ticks, one byte each; a zero is taken as 1 (0x3210). The game calls it from 0x0037939c with settings such as 6 ms and 1 ms, which are 8 ticks and 1 tick at 1280 ticks per second.

Inputs the board drives itself

Not every input is a wire. A driver rule can name an input number that the board sets while the rule's coil is on, and the game reads it like any switch. See Drivers, bytes 34 and 35 of the rule.

The CPU board's own switches

Service buttons, DIP switches and the coin door are wired to the CPU board and never cross the node bus. The cpuspi thread at 0x005b9cc0 opens /dev/spidev1.0, sets 100 kHz and SPI mode 3, and runs full-duplex 8-byte transfers in a tight loop. game cross-check

Coils and motors

A driver is a high-current output of a board: a coil, a motor, a flasher. A pinnode has nine, index 0 to 8; a coil4node eight. Durations are in board ticks, 1280 per second, so 1 ms is 1.28 ticks. A power byte v means (v + 1) / 256 of full power, and 0 means off. Everything on this tab is from the pinnode firmware, handler 0x3498 and service routine 0x1ddc, unless tagged otherwise. firmware

Lamps and LEDs

Every lamp is a brightness channel on a board. An RGB lamp is three channels. To change a lamp the game sends the channel, a brightness and a fade, and the board ramps the output by itself.

Brightness
One byte, the duty cycle, after the game has applied its own curve (table 0x007f8954). Inside the board the target is brightness × 128 + 128, and 0 stays 0.
Fade
One byte. Timed from the game, the unit is 1/60 s: chained fades follow each other at 16.6-16.7 ms per unit. An LED board ticks 60 times a second, which fits. On a pinnode the fade byte selects a step size from a table, which gives the same time whatever the distance. firmware measured
Batch size
The lamp pass at 0x004d7f84 collects channel / brightness / fade triples per board and hands at most 96 at a time to the sender 0x005b0468. The encoder 0x005adf20 packs them.
Pages
A board with more than 96 channels is addressed in pages of 96: channel = page × 96 + index.

The LED update, commands 80 to bf

The command byte is itself a bit field. It says how the brightness and fade values that follow are packed. This section is from the game's encoder and from decoding recorded traffic. game measured

Everything in one byte. Used when the fade bits are anything but 100.

Form B

Fade bits 100 in the command mean a second header byte follows, with the page in its top three bits and the fade mode in the low five.

Brightness modeBytes sent
0None. All channels off.
1None. All channels 0xFF.
2One byte per channel.
3One byte for all channels.
Fade modeBytes sent
0x00One byte per channel.
0x04None. No fade.
0x14One byte for all channels.
0x08 / 0x18Two values and a bitmap choosing between them.
0x0c / 0x1cThe most common value, a bitmap, then one byte per marked channel.

Bit 0x10 of the fade mode means the common value is present in the message. Without it the common value is 0.

Which channels?

After the header comes the addressing. Its first byte decides the kind.

First byte below 0x80: a list

With A = 0, that byte is the one channel.

With A = 1, more channel bytes follow. The last one has bit 7 set.

First byte 0x80 or above: a bitmap

The second byte is first << 4 | last, in units of 8 channels, last at most 11. One bitmap byte per unit, bit j = channel unit × 8 + j.

Bitmap bytes equal to the fill value are left out. The fill value is 0x00, or 0xFF when bit 6 of the first addressing byte is set. Which bytes are present:

SpanRule
1 to 8 unitsThe first and the last byte are always sent. Bit k − 1 of the first addressing byte says whether middle byte k is sent (bits 0-5).
9 to 12 unitsBits 0-3 of the first addressing byte flag bytes 0-3. With A = 1 a third header byte follows and flags bytes 4-11. Without it bytes 4-11 are all sent.

Order of the whole message

cmd  [page<<5|fade]  addressing (list, or bitmap header + bitmap bytes)
     [fade bitmap: one bit per addressed channel; bitmap addressing with fade mode 08/18/0c/1c]
     brightness bytes   (per mode)
     fade bytes         (per mode: common value, second value, or the exceptions)

Firmware and the boot loader

Each board has a boot loader and an application. The application images are on the SD card as /games/<firmware>-<mcu family>-a_b_c.hex. At every start the game compares what each board reports with the image for it, and re-programs a board that differs. All of that runs over the same bus with commands f1 to f8.

The same files are how this guide knows what the boards do: an image can be decrypted outside the game and read. tools/node_fw_decrypt.py does the first, tools/node_fw_ghidra/ the second.

The image file

Intel HEX with two record types of Stern's own. Loaded by fw_image_load 0x005b8270. Application data starts at address 0x1000; the updater never writes below it. game

Record typeContent
00Data, as in any Intel HEX file.
06One record at address 0, 16 bytes: the scrambled image header.
07A table of 16-bit entries, one per 1 KiB page. The record's address field counts entries, not bytes: a record at address 8 holds entries 8 to 15.

The header, after descrambling

fw_header_descramble 0x005b7fb8 applies these in order to the 16 bytes h:

h[6]  ^= h[3] ^ h[2]
h[8]  ^= h[5] ^ h[7]
h[15] ^= h[11] ^ h[7] ^ h[3]
h[10] ^= h[9] ^ h[11]
h[12] ^= h[13] ^ h[9] ^ h[5]
h[4]  ^= h[0] ^ h[1]
ByteField
4, 6, 8Version a, b, c.
10, 12Page count.
14Image id. Reported by the board as byte 10 of its version reply.
15Flag. 0 = the game decrypts the image. 1 = the image is sent encrypted.
othersNot decoded. They differ from image to image and feed the descrambling.

The cipher

AES-192 in CBC mode over the application data from 0x1000. The key is the first 24 bytes of the type-07 table (padded with a5 if the table is shorter). The IV is the header exactly as it stands in the file, before descrambling. In the game: fw_cipher_init 0x005baab0 and fw_cipher_decrypt 0x005babb0. Checked by decrypting all fifteen flag-0 images of the D&D card: each comes out as a stack pointer in RAM followed by Thumb code. game measured

The first twelve entries of the type-07 table are therefore the key, and for a flag-1 image the same table is the list of page check values.

Plain and encrypted images

Header flag 0: every image except node4

The game decrypts the image in memory when it loads it and sends plain pages.

The check value is the 16-bit sum of the page's bytes (fw_image_page_check_value 0x005b8864).

Before sending, the game reads the 64-byte block from the board with f2, copies it into the image after a marker, and recomputes that block's check word (fw_config_block_checksum 0x005b8918). This is how a board keeps its own data across an update. The content of the block is not established.

Header flag 1: node4

The image stays encrypted. The game sends the 16-byte header with f3, then the pages with bit 0x40 set in the address byte.

The f5 reply is compared with the type-07 entry of the page.

Decrypting is left to the boot loader. Where its key comes from was not established, so node4's firmware could not be read. unknown

The simulator, and what is still open

The recompiled game runs against simulated boards in src/runtime. The simulator was first written from the game's side alone. After the firmware was read it was brought in line with it at the level of the protocol: what a board and the bridge reply, and when. What the simulator takes from the firmware

  • Tick rate by firmware name: 1280, or 60 on LED boards. The playfield model converts every duration with the board's rate.
  • The two traffic flags, the mask-and-value form of f0, and the rule that a board answers a poll only with both set. The service mask of 71.
  • The age word after the inputs in the 10 and 11 replies.
  • The reset cause in the fault word after power-up and after f1.
  • The bridge's status word, cleared by reading, starting at "restarted, power-on"; the status byte derived from it; ee and 55 for a board that does not answer.
  • The 0a state byte with the amplifier power in bit 1 and the lamp level in the second byte.
  • The layouts of 40, 41 and 31: start delay, lockout, five triggers, two stop inputs and the run-on time.

What reading the firmware settled

  • The tick rate: 1280 per second on driver and stepper boards, 60 on LED boards.
  • The two bytes after the inputs in the 11 reply.
  • The traffic flags of f0 and how a board answers a poll.
  • Every byte of the driver rule 41, and the optional tail of 40.
  • The stepper set-up 32, the move 31, and commands 34, 36 and 37.
  • Bridge commands 0a, 0b, 0c and 0d, the whole status word, and what the boot hold is.
  • The bits of the board's fault word, the scrambling, and where the identity replies come from.
  • The image cipher and the layout of the type-07 table.

Still open

  • The boot loader: its f3, f5, f6, f7 and f8, how it reacts to the break, and how it decrypts a flag-1 image. It is in no update file.
  • node4, the QR scanner board, and lcdnode: no plain image was read.
  • tmc2590node, hdminode, magsensornode: only their tick rate, image id and command groups were read. Game commands 12, 21, 61, 63, c1-c3, cf, d0, d1 are decoded for the boards studied; what they do on these three is not.
  • pinnode: commands 50 and 5b, most set-up bytes of 51, what plays d0 records, the bit table of 45, the 32-bit setting of 73, the RAM word behind fault bit 7.
  • tmc5041node: the first value of the status reply, and the factors between protocol units and the chip's units.
  • The bridge's clock on the crystal path, and so its times in milliseconds.
  • What a real board holds in its manufacturing record and its 64-byte block.
  • The output bytes of the CPU board's SPI transfer; the colour of single-channel lamps; the board at address 2 on titles that use it.
  • Whether 1.36.0, which Godzilla carries, differs from 1.37.0 in any reply. Only 1.37.0 was read.

Decode a frame

Paste bytes from a SPIKE2_NODEBUS_TRACE log, or a command with its arguments, and read what they say. A full frame is recognised by its length and checksum. Anything else is read as a command with arguments, and the frame for it is built for the address you give. Times are shown in ticks and in milliseconds at 1280 ticks per second.
