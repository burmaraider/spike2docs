The CPU board, from the game's side

The CPU board is a small Linux computer. One program on it, game, is the pinball machine: rules, display, sound and the conversation with the node boards. This page lists what that program touches on the board, and what each thing answers.

Read this first: nothing here was captured from, or run on, real hardware. Everything is read from the software on game cards and from what that software does when it runs against a simulator. Each statement carries one of the tags below.

The pieces

The computer

Processor
A 32-bit ARM. The game is an ELF32 ARMv7-A executable, hard-float, ARM mode only. The serial ports are named ttymxc, the video decoder is /dev/mxc_vpu, and the card carries vpu_fw_imx6d.bin: the names of an NXP i.MX6. card
Kernel
Linux 3.14.28. The module folder on the card is 3.14.28_1.0.0_ga-wandboard+g08f5291; the device tree is stern-spike2.dtb. card
System
Yocto Poky 1.8.2 (/etc/issue), glibc 2.21, libstdc++ 6.0.20. The platform release is in /usr/local/spike/VERSION.txt ("SPIKE v2.7.0" on the Star Wars 1.31.0 card). card
The game
Compiled with GCC 4.9.2, stripped, linked against 25 shared libraries, about 650 imported functions. It starts some twenty threads; the ones that touch hardware are the render thread (display), nodebus (serial port), cpuspi (switches) and the sound engine's. game measured

What the simulator answers

The recompilation's runtime provides /dev/spidev1.0, /dev/i2c-1, /dev/ttymxc1, the ALSA cards and the data devices. Everything else in the table fails the way a missing device does (ENOENT, ENOTTY, EAFNOSUPPORT), and shell commands are not executed. All four games reach their main loop that way. model

The identity record

The first 52 bytes of the EEPROM hold who this machine is, lightly scrambled. The game reads them at start (Godzilla 0x003fb484). game

  1. Word 0 seeds a generator: state = state * 0x19660d + 1 (0x004244a8). The key for a word is state >> 8, and a key of 0 counts as 1.
  2. Each of the next twelve words is one record byte multiplied by its key.
  3. The twelve bytes are: 0..3 the serial number, 4..7 a model code, 8..9 a 16-bit value, 10..11 the inverted 16-bit sum of bytes 0..9 (0x004d9718).
  4. A model code of "999" makes the game use the code compiled into it (0x0070de70; "T7" in Godzilla LE).

The rest of the chip is the game's non-volatile storage; it reads and writes it with a 2-byte offset followed by data.

A simulated board starts with a blank chip (all 0xFF). The runtime writes an identity record into a blank chip, with serial 999999 and model 999, and never touches one that has a record. With blank settings the game shows its first-boot "Guided Setup". model

The codecs on the bus

Each SGTL5000 takes a 16-bit register address followed by 16-bit big-endian data. At start the game reads CHIP_ANA_CTRL (0x0024) of both (Godzilla 0x00336ccc), cycles codec power and polls up to 250 times for the reset value 0x0111 (0x00336e24), then writes the registers listed in a table (0x00336d1c, table at 0x00660c00). Only registers that differ from reset are written. game

What it sets there is on the Sound tab.

The board's own switches

A few inputs are wired to the CPU board and not to a node board: the DIP switches, the service buttons inside the coin door, the door interlock, and the headphone kit. The game reads them over SPI and files them as "node 0".

The cpuspi thread (Godzilla 0x005b9cc0) sets /dev/spidev1.0 to 100 kHz, mode 3, and then exchanges 8 bytes each way without pause: 8 output bytes out (from 0x0085581c), 8 input bytes in (to 0x008557d8). A set bit is an open contact. game cross-check

The service buttons

SELECT enters the service menu and confirms, PLUS and MINUS move, BACK leaves. On a machine with blank settings the same four buttons work the first-boot Guided Setup. measured

What the 8 output bytes do on the board was not followed. unknown

Displays

The game draws with OpenGL ES 2 through EGL, on the graphics driver of the i.MX6 (Vivante). There is no window system: the driver's own framebuffer calls stand in for one.

  1. fbGetDisplayByIndex(n) names a display; fbGetDisplayGeometry gives its size; fbCreateWindow makes a full-screen native window.
  2. eglChooseConfig asks for RGB 5-6-5 with a 24-bit depth buffer; eglCreateContext for client version 2, sharing nothing.
  3. One render thread makes the context current, draws, and calls eglSwapBuffers, about 55 times a second in step with the main loop.

The same function sets up every display (Godzilla 0x5bef10, Star Wars 0x4efde0): it takes a display object and an index and fills in the object's EGL display, config, surface, context, width and height. game measured

Display 0: the LCD

Every title opens display 0, the large LCD in the backbox. The recompilation gives it a 1366 x 768 window; video is decoded at 1360 x 768, and the first entry of Star Wars' timing table for /dev/fb0 is a 1360 x 768 mode. measured game

The display object's set-up takes a rotation argument, 0 or 180 degrees, chosen by a byte of a global of the game (Star Wars 0x426704, the byte at 0x70b994 + 0xc). game

Display 2: a second panel

Star Wars Pro also opens display 2. Godzilla has the same two call sites and never creates the second display object; D&D and Batman open display 0 only. It is /dev/fb2: the game holds a 480 x 272 timing for it (table at 0x5b6750, applied at 0x320904) and it is the small screen on that machine's playfield. game

It has its own surface and its own context, and the render thread switches between the two every frame. Its picture is not drawn in its own context. The LCD's context renders it into a 480 x 272 texture, and display 2's context shows a texture that shares that memory:

On a desktop GPU none of this memory sharing exists; the recompilation gives each display its own window and context and copies the texture on the GPU when the second one is invalidated. model

Batman 66 also has a small screen on its playfield, but it is not a display of the CPU board at all: see the LCD node page.

Video

Video clips are MP4 files with H.264, played through GStreamer 0.10, which on the machine uses the VPU. The game opens /dev/mxc_vpu itself in the newer builds and continues without it. The recompilation decodes with FFmpeg behind the same GStreamer calls. game model

Headphones

The headphone kit adds four inputs on the CPU board: cable detect, headphone detect, and the two phases of a volume knob. With headphones in (0x004d43c8) the game mutes the line output of both cards and puts PCM at the top of its range, so that Headphone alone sets the loudness. Unplugging puts both back. game

The knob is a two-phase rotary encoder. The game counts transitions, one way up and the other down, and moves Headphone by 2 of 127 when the count reaches 3. measured

Not known: where the cabinet codec's headphone output goes on the board, and whether the kernel on the card has a Line Out Mute control at all (the saved mixer state lists none). unknown

What is still open

  • The chip at I2C address 0x68 that the newer builds probe.
  • What the three serial ioctls on /dev/ttymxc1 are for, and whether a game minds their failing. None of the four does.
  • The 8 output bytes of the SPI exchange.
  • The HDMI transmitter: Star Wars opens it and sets timings on two framebuffers; which physical outputs those are was inferred from the timings alone.
  • The connectivity kit: its own card on /connectivity, the conagent program beside the game, the shared-memory blocks and the QR reader board. The recompilation never connects to Stern's servers; these fail as they would on a machine without the kit.
  • Everything about the board that software cannot show: the schematic, power sequencing, what the amplifiers are.
