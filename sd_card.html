What is on a game's SD card

A SPIKE2 machine boots from one SD card. It holds the Linux system, the game, and the space the game writes its settings to. Reading a card image is where the recompilation starts, and this page is what the reader (tools/sd_extract.py) finds on one.

Read this first: nothing here was captured from, or run on, real hardware. Everything is read from card images of current releases. Each statement carries one of the tags below.

Partitions

The card has a DOS partition table with three primary partitions and two logical ones. Sizes are those of an 8 GB image; the game partition takes whatever the card has left (a 16 GB image differs only there). card

Mount points are from /etc/fstab on the card. It also names /dev/mmcblk2p1 on /connectivity: a second card, the connectivity kit's. The Star Wars 1.31.0 and Batman 1.14.0 images carry the same file-system identifiers on every partition, so one base image serves several titles.

The extractor numbers partitions from 0 in table order and counts the extended container, so the three it needs are its partitions 0, 1 and 2.

The system partition

Distribution
Yocto Poky 1.8.2 (/etc/issue). Kernel modules for 3.14.28 (/lib/modules/3.14.28_1.0.0_ga-wandboard+g08f5291).
Libraries the game links
25 in all: glibc 2.21, libstdc++.so.6.0.20, libgcc_s.so.1, EGL and OpenGL ES (Vivante), ALSA, GStreamer 0.10, libcurl, libcrypto and others. The same files, byte for byte, on all four cards read.
/usr/local/spike/
VERSION.txt (the platform release, "SPIKE v2.7.0"), netbridge-0_5_0.hex (firmware of the net bridge), three wireless-adapter kernel modules, fonts, a logo, and spike_menu/: a small game and image.bin of its own.
/etc/asound.conf
The two sound cards and their mixer names; see Sound on the CPU board page.
/etc/init.d/game
Starts the program: it sets GAMES_PATH=/games and SPIKE_MENU=/usr/local/spike/spike_menu/game, and holds the steps that install a new kernel or device tree left by an update.

card

The recompilation takes two files from here, libstdc++ and libgcc_s, and translates them with the game: C++ exceptions are unwound by the original unwinder. Every other library is replaced by native code.

The game partition

The root of /games holds one folder named after the title, three links into it (game, data, conagent), and spk/index/ with a <title>-<version>.sidx file, the index of the update package the card was made from. The title's folder: card

FileWhat it is
gameThe program: 6.6 to 8.2 MB, an ELF32 ARM executable. Everything the machine does is in it.
image.binThe big container, 1.6 to 2.1 GB: sound and the rest of the game's packed data. The game maps it into memory whole. D&D has image-sc01.bin to image-sc29.bin beside it.
assets/lcd/The display scenes: auto_loaded/ and demand_loaded/, each a set of folders named by a hash holding scene.radium and its scene.assets; and GameLogo.png.
assets/nuk/Pictures and fonts of the service menu, among them the playfield, back panel and cabinet pictures the menu draws switches and lamps on.
*-a_b_c.hexFirmware for every kind of node board, seventeen files, whether the machine has that board or not. The game compares each board's version with these and re-programs a board that differs.
conagentA second program, 249 kB, the same on every card read: the connectivity agent.
data/The release notes.

All four executables carry the compiler string "GCC: (GNU) 4.9.2" and need the same 25 libraries. A title's age says nothing about its build: Batman is the oldest SPIKE2 game, and its 1.14.0 is as recent a build as the others.

An update package (.spk) holds only what changed since an earlier release. A full card image is the place to look for a file an update does not have.

Reading a card image

tools/sd_extract.py reads a raw image without mounting it: the partition table, FAT for the boot partition, ext2/3/4 for the rest, including extents. It never writes to the image.

python tools/sd_extract.py inspect <card image>
python tools/sd_extract.py extract <card image> -o card --partition 0 --partition 1 --partition 2

Symbolic links come out as small .symlink files holding their target, and a manifest.json lists every entry. tools/spike2_build.py runs the extraction as its first step and then looks for exactly one game on the game partition.

A card image is the owner's copy of a game. Nothing extracted from it belongs in a repository or on a web page, and these notes contain none of it.
